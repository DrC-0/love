# 判定の派生量は先読みでまとめて作らない

`bf_position` の `hand_e(i)` / `deck(i)` は要素ごとに導出する。8要素ぶんを
まとめて返す形 (`bool[8]`) に変えると 5〜12% 遅くなったので採らない。

理由は早期脱出を失うこと。`open_e()` は候補が2枚見つかった時点で 0 を返すので
平均4反復で終わるし、`draw_win` のループは `if(!all_true) break;` で1〜2反復で
抜けることが多い。先に8要素ぶん作るとこれらが全部無駄になる。

まとめて作る利点として見込んでいた「推論フラグ (`open_flag_e` / `lt5_flag_e` /
`not7_flag_e` / `sol_flag_e`) の判定を要素ごとに8回繰り返す無駄」は、実測では
存在しなかった。`-O2` がループ不変なフラグのロードを外に出しており、残る分岐も
予測が当たる。`hand_e` の呼び出しを 1.67億回から 1.16億回に減らしても実行時間は
増えた、という形で確認している。呼び出し回数が減っても速くなるとは限らない。

これに伴い、当初考えていた「候補集合をビットマスクで `bf_position` に持たせ、
書き換え忘れをカプセル化と不変条件 assert で防ぐ」という案も棚上げする。
持たせても、その値を使う側が早期脱出を諦めることになるため。

なお、遅延評価のまま `open_e()` の呼び出しだけをループから括り出す query
オブジェクトは性能中立だった (決定的カウンタが完全に同一、壁時計は順序を
交互にした8組で勝ち3負け5、中央値の差3%で符号が一定しない)。カプセル化の
ために入れるぶんには代償がない。
