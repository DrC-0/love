# 性能判断に gprof を使わない

`-pg` ビルドの gprof は、このコードベースの性能比率を系統的に歪める。`mcount` が
各関数の入口に挿入されるため、`-O2` なら呼び出し元にインライン展開されるはずの
小さな葉関数 (`hand_e` / `open_e` / `count_deck` / `validate_hand_e_candidate`) が
強制的に out-of-line 化され、その呼び出しコストごと自分の取り分として計上される。
実際 gprof が 8.3% と報告した `validate_hand_e_candidate` は、空関数に置き換えて
交互実行で比較したところ短縮がまったく確認できなかった。加えて libc は `-pg` で
ビルドされていないので、`ef_wizard` が返す `std::vector<bf_position>` のヒープ確保
(部分ゲーム 117 の打ち切り深さ7 で 441 万回) は**プロファイルのどこにも現れない**。

代わりに決定的カウンタを使う。判定器の呼び出し回数を数えるビルドを別に用意し、
その回数の増減で判断する。壁時計は最終確認だけに使い、交互実行の中央値で比較して
10% 未満の差は根拠にしない (同一バイナリ同士でも実行順を変えるだけで 30% 動いた)。

この方法で測り直した結果、履歴文字列からの `bf_position` の再構築は性能上の問題
ではないと分かった。コンストラクタの呼び出しは `hand_e` の呼び出し 1 万回あたり
5 回程度しかない。ここを速くしようとしてはいけない。
