# plan-gate

「Haiku が一発で正しく実装できる計画書になるまで、計画書を書き直す」ためのゲートです。
Haiku は実装役ではなく **計測器** です。Haiku が答えられない設問がある＝計画書に穴がある、
という判定にだけ使います。

## 手順

### 1. 計画書を書く

`.claude/plans/<slug>.md` に書く。最低限これを含めること:

- 変更するファイルと箇所を `file:line` で
- 変更後のコード断片（差分でよい）
- **org と rnd のどちらを触るのか。両方なら両方の変更を別項目として書く**
- 履歴を伸ばす処理を含むなら、末尾を追記するのか payload 付きに置換するのか
- 検証コマンド（例: `make cfr cfr0 cfrorg brrnd brorg win`、`./cfrorg 5 5 7`）

### 2. 設問を作る

`.claude/plans/<slug>.quiz.md` に 5〜8 問。**答えは書かない。**

設問は「**間違えたら実装が壊れるもの**」に限る。計画書を書いた直後、
Haiku の答えを見る前に作ること（後から作ると、答えられる設問ばかり選んでしまう）。

このリポジトリの定番設問（該当する変更なら必ず入れる）:

- この変更は org 側・rnd 側のどちらを触るか。片方だけなら、もう片方を触らなくてよい理由は何か
- 対で存在する関数・ヘッダのうち、どれとどれを同時に直す必要があるか
- 行動履歴に手を入れるか。入れるなら追記か、末尾1文字の置換か
- `bf_position` の `_s` / `_e` のどちらの視点の話か
- 新しく参照するフラグ（`lt5_*` `not7_*` `sol_*` `open_flag_*`）はどれで、その意味は何か
- 変更後に走らせるコマンドと、期待される出力は何か

### 3. Haiku に解かせる

Agent ツールで `subagent_type: "plan-quiz"` を起動する。

渡すのは **計画書と設問のファイルパスだけ**。会話の文脈・設計意図・
「たぶんこう答えてほしい」といった誘導を一切渡さないこと。

> `subagent_type: "fork"` は**使わない**。fork はこちらの文脈を丸ごと継承するので、
> 計画書に書いていないことまで知った状態になり、テストとして成立しない。

### 4. 採点する

- `不明` が 1 つでもある → **不合格**
- 誤答がある → **不合格**
- 総評に書かれた「やらかしそうなこと」が実際に起こりうる → **不合格**

`不明` は Haiku の能力不足ではなく、**計画書の記載漏れ**として扱う。
「これくらい分かるだろう」と思ったら、それが暗黙知なので明示的に書く。

### 5. 落ちたら書き直して再試験

穴を埋めて計画書を改訂し、**新しい plan-quiz エージェントを起動して** 3 に戻る。

> 既存の plan-quiz への `SendMessage` は**禁止**。前回の答えと指摘を覚えているので、
> 改訂の効果を測れず必ず合格してしまう。毎回まっさらな Haiku で測ること。

3 回落ちたら、計画書を直すのをやめてユーザーに相談する
（計画自体が複雑すぎるか、分割すべきサインなので）。

### 6. 合格したら実装

1. 計画書をユーザーに提示し、承認を得る。
2. 作業ブランチを切る（master に直接積まない）。
3. Agent ツールで `subagent_type: "impl"` を起動し、**計画書のパスだけ**渡す。
4. impl が「計画書に書かれていない判断が必要」と言って止まったら、
   それは計画のバグ。1 に戻って計画書を直し、再度ゲートを通す。

## やらないこと

- ゲートを通さずに自分で実装を始めること（このスキルを呼んだ意味が無くなる）
- Haiku の答えを見てから設問を足したり減らしたりすること
- 「今回は簡単だから」と設問を 2〜3 問に減らすこと。簡単なら全問正解して即通過するだけ
